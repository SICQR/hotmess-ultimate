3.2 GDPR COMPLIANCE (EU/UK DATA PROTECTION)
─────────────────────────────────────────────────────────────────────────────

PRINCIPLES:
1. Lawful basis (consent, contract, legitimate interest)
2. Data minimization (collect only what's needed)
3. Purpose limitation (use data only for stated purpose)
4. Storage limitation (delete when no longer needed)
5. Integrity & confidentiality (encrypt, secure)
6. Accountability (audit logs, DPO oversight)

IMPLEMENTATION:
• Cookie consent banner (explicit opt-in for analytics, marketing)
• Privacy policy versioning (track changes, require re-consent)
• Data subject rights:
  - Right to access (export all user data)
  - Right to rectification (update profile)
  - Right to erasure (delete account + cascade delete)
  - Right to portability (JSON export)
  - Right to object (opt-out of marketing)
  - Right to restrict processing (pause automated decisions)

TECHNICAL MEASURES:
• RLS (Row-Level Security) on all Supabase tables
• Encryption at rest (Supabase default: AES-256)
• Encryption in transit (TLS 1.3)
• Pseudonymization (hash emails, mask IP addresses)
• Audit logs (all admin actions tracked)

DATA RETENTION:
• Active users: Indefinite (while account exists)
• Deleted accounts: 30-day grace period → permanent deletion
• Audit logs: 7 years (legal requirement)
• Analytics: 26 months (Google Analytics default)

SUBPROCESSORS:
• Vercel (hosting)
• Supabase (database)
• Shopify (e-commerce)
• Stripe (payments)
• Make.com (automation)
• Telegram (notifications)
• Sentry (error tracking)

FILE LOCATIONS:

4.1 TECHNICAL ESCALATION MATRIX
─────────────────────────────────────────────────────────────────────────────

SEVERITY LEVELS:
• P0 (Critical): Site down, payment failure, data breach
  - Response time: 15 minutes
  - Notify: Duty engineer, CTO, DPO (if data breach)
  - Action: Immediate fix or rollback
• P1 (High): Major feature broken, performance degraded >50%
  - Response time: 1 hour
  - Notify: On-call engineer, product lead
  - Action: Hotfix within 4 hours
• P2 (Medium): Minor feature broken, UX issue
  - Response time: 4 hours
  - Notify: Assigned engineer
  - Action: Fix in next sprint
• P3 (Low): Cosmetic bug, enhancement request
  - Response time: Next sprint
  - Notify: Product backlog
  - Action: Prioritize based on impact

INCIDENT RESPONSE (P0):
1. Detect: Monitoring alert (Sentry, Vercel, Datadog)
2. Triage: Duty engineer assesses severity
3. Communicate: Slack #incidents channel + status page update
4. Mitigate: Rollback, disable feature, or hotfix
5. Resolve: Deploy fix, verify resolution
6. Post-mortem: Write incident report within 24h

DATA BREACH PROTOCOL:
1. Contain: Isolate affected systems
2. Assess: Determine scope (number of users, data types)
3. Notify: DPO, ICO (within 72h if high risk), affected users
4. Remediate: Patch vulnerability, reset credentials
5. Document: Breach register entry, lessons learned

5.3 DATABASE MIGRATIONS
─────────────────────────────────────────────────────────────────────────────

MIGRATION WORKFLOW:
1. Create migration: `supabase migration new <name>`
2. Write SQL in supabase/migrations/YYYYMMDDHHMMSS_<name>.sql
3. Test locally: `supabase db reset` (drops + re-seeds)
4. Commit migration file
5. Deploy: `supabase db push` (applies to remote)

MIGRATION BEST PRACTICES:
• Idempotent: Use `IF NOT EXISTS`, `IF EXISTS`
• Backward compatible: Avoid breaking changes mid-rollout
• RLS first: Enable RLS immediately after table creation
• Indexes: Add indexes for foreign keys, frequently queried columns
• Constraints: Use CHECK, NOT NULL, UNIQUE appropriately

ROLLBACK:
• No automatic rollback in Supabase
• Manual: Write reverse migration, apply via psql
• Prevention: Test thoroughly in staging first

FILE LOCATIONS:
• supabase/migrations/ (all migration files)
• supabase/seed/ (seed data for dev/staging)
• packages/hotmess-all-in-db-secure/db/ (RLS policies, GDPR functions)
